# 社区协作与后续运行

## 决定沟通路线

已有 Issue：核实是否有人进行中，按贡献规则准备有实质内容的回复。新 Bug：查重，带最小复现、版本、实际/预期行为和影响。功能建议：说明真实需求、现有 workaround、方案边界、兼容性和维护成本，按规则先 Discussion/Issue。仓库明确允许的小修复可直接 PR；不强制为 typo 先开 Issue。

不要用空泛“please assign me”刷评论。没有本地复现时用“正在调查/计划验证”，不能套用“已经复现”的模板。认领长期停滞时准备礼貌的接手询问，而非无条件放弃或抢做。

## 发布边界

为具体目的准备准确内容后，检查会话中是否已有对目标仓库、动作和范围的授权。不要让每一次正常本地操作都停下来，也不要把“分析这个仓库”当成发布许可。首次未授权发布时一次说明具体目标和草稿；已有明确授权在范围内继续。

Fork、push、留言、创建 Issue/Discussion/PR 各有不同影响，记录实际授权范围。使用已登录的 GitHub 连接/CLI/浏览器，不读取浏览器凭证数据库或要求用户把 token 发到聊天。认证缺失时先完成可做的本地工作和草稿，再给用户具体登录/发布步骤。可用个人仓库 Git identity 时按仓库局部设置，不能改公司/全局身份。

尊重项目 AI 辅助政策。如实披露要求的协作方式。HUMAN 区、贡献协议与本人声明由本人填写/接受；DCO sign-off 也不替用户虚构认证。若因此需要人操作，引用具体文件/段落和要求，只留下该具体待办，不用泛泛“安全原因”。不伪装 AI 输出为用户亲历或本人写作。

## 推送与创建 PR

本地修复、检查和 PR 草稿准备好后，默认 Fork 路线按以下顺序发布；项目与用户明确采用其他路线时，替换相应仓库，仍核实推送和 PR 的实际两端。已有授权在范围内继续有效，不逐步重复询问。

1. 刷新官方目标分支、Issue 状态和重复 PR，审查相对 base 的最终差异与提交列表，确认只包含本次贡献。若同步或修订改变了代码，执行受影响检查后再发布。
2. 核实当前贡献分支、本地 head SHA 和 Fork 推送远程的实际 push URL（如 `git remote get-url --push --all origin`，远程名按现场替换）。同时检查会改变目标的 push URL/重写配置；有多个推送地址时先厘清，不能把分支同时推到意外仓库。确认目标是用户正确的 Fork，目标分支是本次贡献分支。
3. 显式 Push 到 Fork 的对应分支，标准布局例如 `git push -u origin fix/issue-123`；不用目标不明的裸 `git push`。若远程同名分支已有不同提交，先检查归属和差异，不自动 force。推送后核实远程分支 SHA 与准备发布的本地 SHA 一致。
4. 创建 PR 时明确四个值：head 仓库 = 用户 Fork，head 分支 = 本次贡献分支，base 仓库 = canonical upstream，base 分支 = 项目规定的目标分支。例如 `用户/OpenHands:fix/tab-switch-error → OpenHands/OpenHands:main`，仅在项目要求 `main` 时使用该目标；不要默认把官方目标分支设为与 head 同名，也不要误向自己的 Fork 提 PR。
5. 查询返回的 PR，核实真实 URL、head/base 仓库及分支、head SHA，并记录实际状态。创建请求超时先查是否已存在，不直接重复创建。Push 成功但 PR 尚未创建时，明确记录为“已推送，待创建 PR”。

## PR 内容

先采用当前仓库模板，再填必要信息：
- 具体触发场景和用户影响。
- 根因与最小修改，说明关键取舍。
- 相关 Issue；只有确实完整解决且适合自动关闭时才用 `Fixes #...`，否则用 `Refs #...`。
- 实际执行的检查、修改前后证据；未执行的检查及原因。
- 仓库要求的截图/录屏、文档、发布说明、兼容性信息。

正文面向未读过聊天的工程师，省掉过程流水账和夸大宣传。不能把本地路径链接当成公开证据；需要上传的材料先整理成不含敏感信息的可发布版本。

发布前还需核对当前 CI 要求和模板；按上面的推送与 PR 检查确认远程结果，不能仅凭本地草稿或命令已发出声称投稿成功。

## CI 与 Review

跟进时核对 PR 当前 head SHA、状态与最近事件；不要用旧 commit 的绿色 CI 为新代码背书。

| 观察 | 行动 |
|---|---|
| 本次变更造成失败 | 定位 job/command/test，最小修复并重新验证 |
| 无关基线失败/环境故障 | 对照证据，说明限制；不擅自扩大改动 |
| fork CI 等待维护者批准 | 记录等待，不修改安全工作流来绕过 |
| Changes requested | 逐项理解，处理后用文件/测试依据回复 |
| 方向分歧或新范围 | 说明技术取舍，必要时请求明确方向 |
| 已有授权范围内的修订 | 继续修改、验证和推送；不重复索取同样许可 |
| 合并冲突 | 保护未提交内容，按项目惯例同步并重新验证 |
| 明确不接受、被替代、关闭 | 查原因并结束/调整；不重复发同类 PR |
| Approved | 仍非 merged，等待或按明确权限处理 |
| Merged | 读取 merged_at/merge commit，保存证据 |

Review 讨论不必机械迎合错误建议，但应围绕项目约束、事实和方案沟通，不长篇争辩。没有事件就不反复评论催促。

## 可选的定期检查

仅用户明确请求“定期看/提醒/监控”时启用。优先使用宿主提供的自动化工具，先查已有安排，避免重复创建。工具不可用时明确只能手动再次调用；skill 文件本身不会定时运行。不要自行加 cron、开后台无限循环或声称已监控。

计划的 prompt 应包含：仓库和 Issue/PR 精确链接、个人记录绝对路径、上次已处理的事件/时间、用户授权范围、检查和停止条件。每次只读取必要增量；无变化不发通知，仅新 Review、失败、合并、关闭或需要用户操作时提醒。合并/关闭后按用户期望结束该 PR 的监控；若同时授权仓库机会雷达，单独保持其目标。

维护者反馈需要公开回复时仍遵守原授权，不把定时读取授权扩大成对外发言授权。观察到变化后更新记录；没有确认运行句柄或自动化配置时不能声称已在持续运行。
