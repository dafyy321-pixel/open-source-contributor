# 复盘与持续贡献

在用户请求总结、一次贡献结束或实际反馈值得沉淀时使用。复盘可以针对未合并、被替代或成功复现的贡献，不只记成功。

## 证据记录

读取实际 Issue/PR、commit、测试输出、Review 和最终状态，整理：
1. 用户场景与影响；来源和确认程度。
2. 调查路径、根因、有效修复及关键取舍。
3. 修改前后验证，哪些环境/场景未覆盖。
4. 维护者反馈如何改变了方案。
5. 用户与 AI 各自实际完成的工作；没有确认的个人经历不代写。
6. 当前结果：报告、复现、草稿、已提交、已合并、已发布、关闭/撤回。

PR URL、状态检查时间、commit 和测试是证据；“预计提高性能”“应该影响很多人”不是已测成果。Approved 不等于 merged；merged 不等于出现在 release。引用用户影响/性能收益必须有数据和测量范围。

## 输出可选内容

- 简短技术复盘：问题 → 根因 → 修复 → 测试 → Review → 实际结果。
- 面试素材：帮助用户解释三个问题——如何触发、为何这样修、怎样证明。解释用户尚不理解的部分，不声称用户已独立完成或精通。
- 简历条目草稿：准确贡献内容和状态，附可公开核验的链接。未合并就写“提交/调查”，不能包装为“已合并”。不以微小修改声称拥有项目核心模块。
- 文章提纲：保留验证和取舍，可附最小公开复现。发布到博客/作品集是另一个动作，需要相应授权。
- 下一次贡献建议：优先同模块、上次 Review 中的真实后续需求、维护者已确认事项。保持一个主要项目的连续理解，但不强制只贡献某几个品牌项目。

## 长期目标的实际衡量

不用 PR 数量或绿格子作为唯一 KPI。记录有效问题数、证据质量、本人可解释程度、掌握的模块、Review 中反复出现的改进、外部采用情况及同项目连续协作。小型文档/测试贡献可以有实际价值，不做固定职业价值排名。

对目标冲突给出具体取舍：快速首次贡献、长期模块深入、职业关联和学习成本分别说明。阶段性成果支持职业积累，但不能承诺求职收益或被维护者认可。

把可复用的**项目惯例**放该仓库的个人记录，并保留来源和日期；不要因一次 Review 就修改整个 skill 的通用规则。不会自动创建个人项目、经营社交账号或写入公司资料。
