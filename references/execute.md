# 调查与实现

## 进入条件

用户选定问题并要求深入调查或修复。请求只限复现时不扩大到修复；请求修复时在已有范围内自主推进。阅读相关贡献约定和当前工作记录，刷新 Issue、评论、相似 PR、默认分支和目标版本。新功能需按仓库要求先达成方向；没有回复不能视为认可。

## 仓库与贡献分支

1. 检查现有 checkout、Git status、origin/upstream、分支、未提交修改及运行中的相关进程。保护用户改动；优先隔离 checkout/worktree。不要把个人开发与公司仓库、数据、Git 身份混用。
2. 核实 canonical upstream、项目规定的 PR 目标分支、当前 GitHub 账号及已有 Fork 的归属和 fork 关系。目标分支可能是 `main`、`master`、`develop` 或维护分支，不能硬编码为 `main`。
3. 正式贡献默认创建或复用自己的 Fork，首次获取代码时 Clone 自己的 Fork。仅调查/复现可以直接 Clone 官方仓库，Fork 不是其前置条件；需要发布能力但认证或授权尚缺时，继续完成可做的本地工作和草稿，再按 [社区协作](collaboration.md) 处理。项目明确要求其他贡献方式或用户指定既有布局时按实际要求执行。
4. 默认远程关系为 `origin = 自己的 Fork`、`upstream = 官方仓库`。已经 Clone 官方仓库时复用本地代码和提交，不删除重来。先核对 fetch/push URL 和分支 tracking；若 `origin` 指向官方且 `upstream` 名称空闲，可将其重命名为 `upstream`，再添加 Fork 为 `origin`。已有同名远程或用户布局时不盲目覆盖；可保留名称并明确记录“官方来源远程”和“Fork 推送远程”。检查实际 URL，不能仅凭远程名判断归属；显示和记录时排除凭证。
5. Fetch 官方目标分支，为一个贡献从其最新 remote-tracking ref 创建独立分支，记录基线 SHA。标准布局例如 `git fetch upstream` 后 `git switch --no-track -c fix/issue-123 upstream/main`；名称和目标分支需替换为已核实值。若工作区有其他改动，使用独立 worktree/checkout，不自动丢弃或挪走用户内容。恢复已有贡献时先核对原分支和 PR，再按项目惯例同步，不重建或覆盖分支。
6. 本地及 Fork 的默认分支保持干净，不直接用于贡献提交；需要更新本地默认分支时，在干净现场使用 `git merge --ff-only upstream/<目标分支>` 等快进方式。出现分叉先检查独有提交，不盲目 pull、reset 或强制覆盖。创建贡献分支可直接基于官方 ref，无需先推送 Fork 默认分支。

同一 PR 的后续修订继续使用其原分支；下一项独立贡献重新 Fetch，从最新官方目标分支开新分支，不从旧贡献分支继承未合并的修改。不要向官方仓库直接推送贡献分支，除非项目路线和用户授权明确允许。

## 开发环境

1. 从 manifests、锁文件、工作区定义、CI 和开发指南推导版本、包管理器、目标包、安装/测试命令；不要按语言套用猜测命令，不静默升级依赖或改全局 Git 配置。
2. 优先现有可用运行时和隔离依赖。`python` 可能是 Windows 商店占位命令，检查实际执行结果；可用绝对路径运行已安装 Python。helper 使用标准库，缺 Python 时可用现有工具按记录 schema 管理，不为它先配置整个项目环境。
3. 优先最小相关模块、示例或测试。不要为了纯逻辑问题先启动全产品，也不要执行仓库提供的任意安装命令而不读用途。费用、需新服务/凭证、显著扩大机器配置时给出具体必要性和替代方案，按现有授权处理。

## 环境替代的边界

| 问题 | 可以尝试 | 不能声称 |
|---|---|---|
| 纯逻辑/异常处理 | 目标单元测试、直接调用相关模块 | 导入失败就是目标 Bug |
| UI 状态/文案 | 组件测试、前端 dev、项目已有 API mocks | mock 通过证明真实后端兼容 |
| API/模型调用逻辑 | 项目既有 stub/fixture、确定性的失败响应 | 模拟服务覆盖真实模型质量/计费/网络行为 |
| Docker、Linux 权限、挂载 | 必要且可用的相同语义环境 | Windows 函数测试证明容器缺陷已修 |
| 数据库/分布式行为 | 匹配引擎和事务语义的测试服务 | SQLite 替代 PostgreSQL 后证明并发一致性 |
| 性能 | 可比较的数据集、环境和基线 | 一次主观变快或无基线即性能收益 |

没有有效等价环境就记录已完成的部分，给出剩余验证的具体路径/成本。确实无法继续时留下可恢复状态或推荐更轻任务，不能通过跳过测试、改变功能语义、关闭安全检查解决环境限制。

## 复现、根因、范围

保留问题版本；必要时在最新支持版本或目标分支复核。分清“旧发布存在而 main 已修”和“main 回归”。记录最小输入、环境、步骤、实际/预期行为及原始输出。最小数据使用公开或合成数据，不复制公司日志、客户数据和密钥。

沿实际代码追踪入口 → 状态/服务 → 失败路径 → 输出 → 现有测试。只扩展与假设有关的路径，不做没有边界的全库审计。代码闻起来不对、注释陈旧或 TODO 不能独立证明用户可见 Bug。

如果无法复现：检查版本/配置、比较已修代码、减少输入；一轮有根据的尝试仍无结果则报告证据缺口，不不断猜修。涉及安全漏洞时先查 SECURITY.md 并准备私密报告路线，不把可利用细节自动发布成公开 Issue。

有自动化条件的代码 Bug：
1. 添加或复用稳定复现测试。
2. 在未修代码上确认失败确实由目标缺陷引起，保存运行结果。
3. 最小修复，遵循仓库边界、风格、兼容承诺与依赖约束。
4. 同一测试通过，执行相关回归和仓库必须检查。

文档/示例/UI/平台问题使用对应的链接检查、示例执行、截图/录屏或平台验证。不添加只重复实现或不验证真实行为的测试。

## 本地完成检查

- 差异只包含本次贡献；无密钥、无意的格式化、临时调查材料、无关锁文件变化。
- 检查问题路径及相邻正常路径；测试有合理断言和确定性。
- 按项目要求执行 lint、typecheck、tests、build、文档/视觉检查。脚本名称从仓库确认。
- 将失败分类为本次引入、原有失败、环境限制、未知原因。必要时在干净基线对照；不得谎称全部通过。
- 记录命令、退出码、相关输出、环境、commit 和修改前后对照。日志先排除凭证/个人资料，发布前再检查。
- 阅读最终 diff，确认方案符合项目设计。需要的新文档/发布说明按模板准备，不为了“最小”省掉必要内容。
- 提交前检查 `git status`、未暂存和已暂存差异；只暂存本次相关文件或 hunks，不把 `git add .` 当成默认动作，不夹带用户原有的暂存内容。确认当前为本次贡献分支后 Commit；message 使用项目惯例，不强行套 Conventional Commits 或未经必要性重写公共历史。Commit 只是本地版本记录，不代表已 Push 或已创建 PR。

完成本地工作后转 [社区协作](collaboration.md)，交付 PR 标题/正文、验证证据、尚未完成的验证、分支及待发布内容。尚缺验证时明确为草稿；不能将 `ready_for_pr` 理解为可承诺合并。
