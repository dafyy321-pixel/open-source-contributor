# 研究与选题

## 路线选择

由用户选择 A（参与已有 Issue）、B（主动发现新问题）或 A+B；不默认 B。没有明确路线时给出简短选项，等待期间可只读核实官方要求，不擅自开始扫描。已有明确路线、指定问题或代选授权时直接执行。路线选择不等于授权发布，也不等于选择了最终修复候选。

## 1. 先取得足够的一手资料

核实仓库 canonical URL、默认分支、是否归档/只读、代码归属、主语言、包与子项目边界。用户给 fork 时确认要贡献到哪个 upstream；企业 GitHub 或私有仓库只用明确授权的连接和来源。

读取 root、.github、docs 等实际存在的位置，以及项目明确链接的贡献资料：
- README、LICENSE、CONTRIBUTING、开发/测试说明、相关 AGENTS.md。
- Issue/PR 模板、CODE_OF_CONDUCT、CODEOWNERS、AI 辅助贡献政策、CLA/DCO 要求。
- 仓库可能继承组织 `.github` 的默认社区文件；仓库未找到贡献指南不能立即得出“没有规则”。
- 当前发布记录、路线图、支持的平台/版本、已知限制、CI 必需检查。

输出规则须包含：要求是什么、适用哪类贡献、文件/段落链接、检查时间。小修复是否可直接 PR、哪些工作须先讨论、认领是否必须，分别记录。不存在普遍的“必须先 fork/先留言/等两周”规则。

## B：主动发现问题

扫描前主 agent 核实上节官方材料，包括组织继承规则、近期维护者说明、Issue/PR 模板、AI 政策、CLA/DCO、本人声明、支持版本、目标分支、必需检查和安全入口。把适用要求、来源和未确认项传给各 subagent；未找到规则不等于没有限制。

在用户选择的项目与范围内，从真实使用路径、官方快速入门、示例、配置和现有测试寻找异常。先明确探索边界与环境成本，用已有环境做最小验证，不自动安装重环境或开展无边界全库审计。A+B 中的 B 部分遵循相同规则。

**必须使用多个 subagent（至少 2 个）分工探索，不能由主 agent 切换角色冒充。** 按项目特点分配独立模块/场景，例如使用流程与示例、核心逻辑与异常传播、平台兼容与依赖、文档契约与测试覆盖，不要求每次覆盖全部维度。主 agent 共享官方规则、目标版本、已查线索和淘汰记录，交叉核实并合并结果；子 agent 不并发写同一 case。并发额度不足时分批调度；完全没有 subagent 能力时说明限制，请用户决定是否接受单 agent 替代，不声称完成多 agent 扫描。

子任务提示词骨架（补充实际模块、规则来源和范围）：

> 在官方贡献规则和本次授权范围内，调查指定模块/场景中有真实价值、可验证、范围合理的问题。从实际使用、文档契约、代码和现有测试检查异常、错误路径及边界条件，不把代码偏好或缺少某功能自动当作 Bug。发现线索后，先核实认领、关联/相似 PR、已合并修复和发布版本，再投入较大复现成本。返回实际影响、预期行为依据、触发条件、版本、来源、复现状态、参与状态、预计改动、验证成本和未知项，也返回淘汰线索及原因。不要完整实现修复、修改共享记录或对外发布。

主 agent 合并同一问题，区分 Bug、配置错误、文档问题和功能建议，最多推荐 5 个候选，各给理由供用户选择。尚待验证的探索方向只能标为调查候选，不能称为已确认 Bug；选定后按 [社区协作](collaboration.md) 的新问题路线推进。

## 2. 判断协作是否真实开放

第一轮少量代表性抽样即可，通常先看近期约 5–10 个相关 PR，包括已合并和关闭未合并，再根据证据缺口扩大。不要固定下载所有历史或强行等待观察期。

- 人类维护者是否回复、Review 和合并外部贡献？机器人活跃不能代替人类响应。
- 使用具体 Review 理解范围、测试、风格和文档要求；不要猜维护者性格。
- 外部身份不确定时标未知。`author_association` 是参考，不足以完整证明就业关系或权限。
- 关闭未合并可能是重复、替代、撤回、实现不合适或需求不接受。阅读原因再分类。
- 若报告响应时间/比例，说明样本数、时间范围和定义；样本只代表被观察的部分。不把仍开放 PR 的等待时长当最终合并耗时。

## 3. 多来源找问题

先核实项目身份和官方规则，再结合仓库与外部来源发现机会。外部报告无需已有 GitHub Issue 才能进入调查；官方贡献规则决定投稿边界，用户体验线索按其具体证据判断。

### 发现与选择信息源

从项目 README、文档、官网中的社区入口，以及中英文项目名、别名、包名的公开搜索，发现相关渠道；用户指定的渠道也纳入考虑。按项目相关性、近期有效讨论、原始材料可读性和当前证据缺口选择来源，并记录选择或未覆盖的原因。不能仅因 GitHub 已有几个候选就省略相关外部渠道的发现；明确指定问题时则围绕该问题查询，不重做全平台调查。

信息源包括但不限于下表。平台名称是示例；允许沿链接和新线索继续加入其他来源，不设平台数量上限，也不要求每次遍历所有平台。

| 信息用途与来源示例 | 寻找 | 核实方法 |
|---|---|---|
| 项目规则与进展：GitHub Issues / Discussions / PR / Review、官方文档、路线图、Releases | 明确故障、维护者确认的需求、未解决讨论、遗漏场景和回归 | 读描述、评论、关联 PR 和发布记录，核实当前处理状态 |
| 开发者讨论与问答：Reddit、Hacker News、Stack Overflow、知乎、V2EX、牛客 | 具体报错、兼容问题、集成困难、重复疑问 | 找原始场景、版本、配置和后续解答 |
| 社交反馈与使用分享：X / Twitter、小红书、博客、技术文章 | 实际使用障碍、workaround、尚未进入 GitHub 的问题 | 追溯原帖和引用，区分使用报告、转载与泛泛评价 |
| 视频与演示：YouTube、TikTok、B站及可访问评论 | 操作失败、教程过时、步骤缺失、实际使用场景 | 分别记录读到的字幕、评论或观察到的画面；保留相关时间点 |
| 项目社区：官方论坛、Discord、Discourse、邮件列表等可访问渠道 | 反复出现的问题、临时解决办法、维护者解释 | 确认项目归属，读取相关上下文和后续结论 |
| 包分发与依赖生态：PyPI、npm、conda、容器镜像仓库、下游项目 | 安装失败、依赖约束、平台兼容、发布包与源码差异 | 核对实际包名、版本、元数据、发布产物和所属仓库；下载量不能证明缺陷 |
| 直接技术证据：文档、示例、测试、相关代码、下游集成代码 | 文档与行为不一致、错误路径、边界条件 | 先作为假设，找准负责的仓库/模块；选题后再本地验证 |

### 从探索搜索到问题追踪

尚无具体问题时，用仓库全名、项目唯一标识、包名或中英文别名，搭配使用体验、安装、报错、兼容、迁移等词做有界探索。出现线索后，转为精确报错、功能名、版本、环境或症状（如 timeout、Windows、streaming），沿原帖、评论和引用跨平台追踪。不要只搜索泛泛产品评价，也不要先要求用户提供一个已确认 Bug 才开始找机会。

每条有价值的线索核实：
- **项目与责任归属：** 区分同名项目、开源仓库、商业托管服务、第三方封装和下游插件；判断应贡献到源码、打包发布、文档还是下游仓库。
- **原始报告与独立性：** 合并同一事件的转载、截图搬运和相互引用；多个平台出现不等于多个独立用户报告。无法追到原始来源时标明不确定性。
- **可见内容：** 区分搜索摘要、正文、评论、字幕和视频画面。只见标题/摘要不能声称已读全文或看过演示；不可访问部分按 [工作记录与工具](records.md) 记录。
- **时间与版本：** 同时记录内容发布时间、检查时间和受影响版本；新帖子可能使用旧版本，源码已修也可能尚未发布到 PyPI/npm 等渠道。
- **技术事实与需求：** 回查所有状态的 Issue/PR、发布记录、文档和当前代码，核实触发条件、配置和已有修复。一个抱怨帖子不是已确认 Bug 或需求批准；证据强弱由材料内容决定，不按平台名称或热度预设。

搜索范围按证据需要扩展。完成相关渠道探索、候选已足够支持用户选择且关键缺口已有结论或明确标注，或继续查询主要得到重复、过时、无关信息时结束；遵守用户的时间和成本约束。最终最多推荐 5 个，不限制来源、查询或内部线索数量，也不以发现第 5 条线索作为自动停止条件。没有合适机会时说明调查范围与缺口，不无限搜索或凑数。

可用 GitHub 搜索起点（替换 owner/repo，实际结果仍需逐项查看）：
```text
repo:owner/repo is:issue is:open label:"help wanted"
repo:owner/repo is:issue is:open label:bug sort:updated-desc
repo:owner/repo is:pr is:merged sort:updated-desc
repo:owner/repo is:pr is:closed is:unmerged sort:updated-desc
repo:owner/repo is:pr "关键症状"
```
标签不存在就按文本、维护者确认和具体用户场景寻找。搜索所有状态的 Issue/PR 来查重复，不能只看 open。GitHub REST Issues 列表包含 PR，必须辨别 `pull_request` 字段。

## 4. 筛选与证据层级

### 参与状态检查

三个检查点：深入代码调查或重环境前快速筛查；推荐前补齐关键证据；用户选择后、正式修复前刷新变化。发布前继续检查，中断恢复、明显时间间隔或新的关联事件也应刷新，不重复全仓调查。

对 A、B 和外部线索一视同仁：读 Issue 当前状态、认领评论和后续进展、Development/timeline/交叉引用；搜索所有状态的 Issue 和相似 PR（含 draft、关闭未合并、已合并），结合症状、模块、报错和引用编号，不能只搜标题或只看 Assignees。跟随相关关联项，核实覆盖范围、目标分支、合并状态和发布版本。open 不证明未修，closed 不证明已修，merged 不证明已发布。读取失败、分页未读完或搜索不完整时，补齐决策所需材料或保留待核实。

| 参与状态 | 决策 |
|---|---|
| 未发现占用，问题仍存在 | 可推荐，附检查范围和时间，不保证绝对无人处理 |
| 已有人推进或有效 PR | 不推荐重复实现；有明确剩余价值时推荐补复现、测试或 Review |
| 已认领但进展不明 | 标为需确认可接手，下一步是沟通，不直接开工 |
| 已修复、未发布 | 排除重复代码修复，核实是否有文档或发布说明贡献 |
| 部分修复或独立遗漏 | 写清已有覆盖和剩余问题，只推荐未覆盖范围 |
| 状态无法核实 | 仅作为待核实调查候选，不推荐为可直接修复 |

每项推荐展示参与状态、相关 Issue/PR、最后检查时间及下一步（调查、确认接手、补证据或修复）。缓存淘汰原因和来源，下一轮优先刷新有变化的项，避免重复深挖。无法排除未公开的工作和检查后的变化，不承诺杜绝重复。

每个候选依次回答：
1. 当前版本确实还有这个问题吗？是否已发布修复、只是安装了旧版本？
2. 属于缺陷、配置错误、文档问题、产品设计还是新功能？影响是什么？
3. 项目欢迎这种贡献吗？有没有维护者确认或使用场景证据？
4. 是否已有认领、分支、关联或相似 PR？检查时间是什么？
5. 哪个仓库/包/模块负责？能否以合理成本验证？
6. 所需环境、依赖、外部服务、风险和未知项是什么？
7. 能带来哪些工程经验，是否延续用户之前的贡献？

证据层级独立于推荐等级：
- 外部报告：别人描述的故障，未独立验证。
- 代码线索：代码似乎支持一个假设，尚无执行证据。
- 本地复现：指定 commit、环境、步骤下观察到失败。
- 修复验证：修改前后对照和相关检查支持修复。

第一轮只能看到代码线索时照实写，不夸大为“已确认 Bug”。“未发现有人处理”也应附检索范围，不能宣称全网无人处理。

先排除不接受贡献、已解决、需求被否定或无法合理验证的选题，再比较价值与成本。四个目标不必算成一个总分：指出哪个最适合快速首次贡献，哪个有长期模块价值，哪个与职业方向关联强。没有合适选题时给下一种有效调查方法或换项目建议。

## 5. 默认交付

开头：推荐 / 有条件推荐 / 暂缓 / 证据不足，附最关键理由。项目适合长期参与与当前有无可做问题分别下结论。

正文保持可决策：
- 项目职责与贡献入口。
- 必须遵守的规则及来源；AI 政策/协议等未查实处明确标注。
- 外部贡献协作情况：代表性已合并与未合并 PR 的观察，不用 Star 代替。
- 调查范围：实际查询的渠道及选择理由、日期、样本；区分找到线索、已查无相关结果、无法访问、仅摘要可见和本次未覆盖，不声称搜遍全网。
- 编号列出最多 5 个经过筛选的推荐候选，便于用户选择；数量上限只适用于最终推荐，不按平台分配名额，不为凑满 5 个降低标准。

每个推荐候选包含：问题与实际用户影响或明确需求、类型、证据等级和原始来源链接、当前版本/状态、重复工作检查、涉及模块与预计改动范围、可行的复现/验证办法、时间/环境成本及主要不确定性、推荐理由、下一步。推荐理由要结合该问题的价值、证据、范围、成本及用户目标说明为什么值得推进，不能只写“适合新手”或“热度高”；如有排序，说明关键取舍。时间只能是带假设的估算，不能保证当天合并。

报告最后可标出一个首选并说明相对优势，但保留其余推荐候选及各自理由，等待用户按编号或问题选择后再推进。即使只有一个合适候选，也不把推荐当作已获修复授权；没有候选时直接说明，不要求用户空选。不重复询问已知语言和目标；用户已经给定问题或明确授权代为选题并推进时，沿用该授权，不再等第二次选题。准确说明当前是否有发布/认领，不能把草稿写成已发布。
